# Protocol test vectors

Every implementation of the mobile protocol (TypeScript in `protocol/ts`, Swift in `ios/DevToolKit`) must reproduce these files exactly. The normative spec is [protocol/SPEC.md](../SPEC.md), §5.

- `official/` holds third-party vectors, copied verbatim. They prove the Noise implementation is correct and not just consistent with itself.
- Everything else is generated by `node protocol/ts/generate-vectors.ts` from fixed seeds. Don't edit those files by hand. `protocol/ts/vectors.test.ts` fails if a regeneration would change them.

## Conventions

- **Bytes are lowercase hex** unless a field is named `…B64u` or is a protocol string that is b64u on the wire (`nonce`, `uri`, anything inside a `json`/`hello` string).
- An empty payload is `""`.
- Roles: the **phone** is always the Noise initiator and the **desktop** the responder.
- Every file has a `description` string. Ignore it.

## `official/noise-ik-25519-aesgcm-sha256.json`

`{ description, vectors: [...] }`. Each vector comes from cacophony, snow or noise-c (`source`, `url`) and keeps their field names:

| field | meaning |
|---|---|
| `init_prologue`, `resp_prologue` | prologue (the same on both sides) |
| `init_static`, `resp_static` | X25519 **private** keys |
| `init_ephemeral`, `resp_ephemeral` | X25519 **private** ephemeral keys to inject |
| `init_remote_static` | responder static **public** key (the `<- s` pre-message) |
| `handshake_hash` | optional; `h` after message 2 |
| `messages[]` | `{ payload, ciphertext }`, alternating initiator → responder, responder → initiator, … Messages 0 and 1 are the handshake; after `Split()` the rest are transport messages, and the alternation continues. |

## `noise-ik.json`

`{ description, vectors: [...] }`. Each vector (`name`: `pair`, `resume`, `empty-payloads`):

| field | meaning |
|---|---|
| `protocol` | `Noise_IK_25519_AESGCM_SHA256` |
| `prologue` | hex of `utf8("devtool-mobile-v1")` |
| `phone.static`, `phone.ephemeral`, `desktop.static`, `desktop.ephemeral` | `{ priv, pub }` X25519 raw keys. Inject the ephemerals. |
| `msg1`, `msg2` | `{ payload, ciphertext }`. The payload is the UTF-8 JSON handshake payload (§4.3). `ciphertext` is the full Noise message, *without* the frame-kind byte. |
| `handshakeHash` | `h` after message 2 (the same on both sides) |
| `transport[]` | `{ from: "phone" \| "desktop", payload, ciphertext }` in send order. The phone sends with `k1` and the desktop with `k2`, and each direction's counter starts at 0. The AES-256-GCM nonce is 4 zero bytes followed by the counter as a big-endian u64. Includes back-to-back messages from one side and an empty payload. |

## `derive.json`

| field | meaning |
|---|---|
| `secrets[]` | `{ secret, relayToken, pairProof, tokenHash, tokenHashB64u }`: `relayToken = HKDF-SHA256(secret, salt = empty, info = "devtool-relay-token-v1", 32)`, `pairProof` the same with `info = "devtool-pair-proof-v1"`, `tokenHash = SHA-256(relayToken)`. `tokenHashB64u` is what goes into the relay `offer`. |
| `deviceIds[]` | `{ seed, pub, deviceId }`: Ed25519 seed → public key → device ID (lowercase hex of the first 16 bytes of SHA-256(pub)) |
| `x25519[]` | `{ priv, pub }` raw X25519 private → public |
| `x25519Dh[]` | `{ priv, pub, shared }` raw X25519 |

## `relay-auth.json`

`vectors[]`: `{ ed25519: { seed, pub, deviceId }, role, nonce, payload, sig, hello }`

- `nonce` is the b64u string from the relay's `challenge`, and it is signed **as that string**.
- `payload` is the hex of `utf8("devtool-relay-v1\n" + role + "\n" + nonce)`.
- `sig` is the hex Ed25519 signature of `payload` (deterministic, RFC 8032).
- `hello` is the exact JSON text of the `hello` message. The third vector is a pending phone with `pair: { to, token }`.

## `pairing-uri.json`

- `valid[]`: `{ payload, uri, note? }`. Decoding `uri` must give `payload`. When there is no `note`, encoding `payload` must also give exactly `uri`, which means JSON keys in the order `v, relay, id, x, e, s, n, exp`, no whitespace, then b64u. The entry with a `note` has unknown JSON fields that decoding drops.
- `invalid[]`: `{ reason, uri }`. Decoding must fail. Expiry is **not** tested here. It is a separate check (`isPairingExpired`), so the UI can say "expired" instead of "invalid".

## `app-messages.json`

Each sample is `{ json, expected }`. Parse the `json` string with the matching parser and compare the result to `expected` (plain JSON equality). Unknown fields must be gone, and absent optional fields must stay absent.

| field | parser |
|---|---|
| `phoneHello[]` | message 1 payload |
| `desktopHello[]` | message 2 payload |
| `appMessages[]` | transport message. `expected: null` means "unknown type, ignore it". A `req` with an unknown `op` still parses, and the receiver answers `unsupported`. `res` keeps `result` as raw JSON (for `inbox.get`, validate it as an `Inbox`). A missing `error.message` becomes `""`. |
| `inboxWithUnknownFields` | `Inbox` from a newer desktop: extra fields are dropped, `null` optional fields are treated as absent, an unknown tab `type` is kept as a string, and an unknown `status` becomes `"idle"` |
| `invalid.phoneHello[]`, `invalid.desktopHello[]`, `invalid.appMessages[]` | JSON strings that must fail to parse |
| `versionNegotiation[]` | `{ local, remote, result }`: `negotiateVersion(local, remote)` returns `{ ok: true, version }` or `{ ok: false, update: "local" \| "remote" }`, where `update` names the side that is too old |

## `fragments.json` (§6.1)

| field | meaning |
|---|---|
| `chunkSize` | 60000: the largest chunk, and the largest message sent whole |
| `message` | `{ id, length, sha256, hex, fragments[] }`: a 150000-byte JSON message (`hex`) split with fragment id `id` gives exactly `fragments` (hex, each `01 id:u32be i:u16be n:u16be chunk`). Feeding `fragments` in order to a receiver yields `hex` on the last one and nothing before. The first chunk boundary falls inside a two-byte UTF-8 character, so chunks must be joined as bytes before decoding. |
| `boundaries[]` | `{ note, length, sha256, fragmentCount, lastFragment? }`: a message of exactly 60000 bytes is sent whole (1), one of 60001 bytes as 2 fragments; `lastFragment` is the second one's hex (fragment id 0) |
| `scenarios[]` | `{ name, steps[] }`. Start a fresh receiver per scenario and apply the steps in order. A step is `{ input, output }` (push the `input` plaintext hex; the receiver yields the complete JSON message `output` as hex, or `null` for nothing) or `{ reset: true }` (a session reset, which forgets partial messages). Covers out-of-order and interleaved fragments, a repeated chunk, `n` changing, `n < 2`, `i >= n`, a header with no chunk, an unknown first byte, the fifth concurrent partial message (dropped; the four already partial are kept), and reusing an id. The 30 s timeout isn't covered here. |

## `chat-messages.json` (§6.2–§6.4)

Each sample is `{ json, expected }` (plus `op` where the parser needs it). Parse, then compare to `expected` with plain JSON equality.

| field | parser |
|---|---|
| `requests[]` | transport message (`parseAppMessage`). A `req` keeps `params` as raw JSON; `params: null` is absent. |
| `params[]` | `{ op, json, expected }`: the desktop's `params` parser for `op` (`parseChatParams`). `chat.earlier` clamps `limit` to 100; `allow` with `always: false` drops `always`. `expected: null` means `op` isn't a chat op. |
| `results[]` | `{ op, json, expected }`: the phone's `res.result` parser for `op` (`parseChatResult`). Results of `chat.close`/`send`/`answer`/`interrupt` normalize to `{}`. `expected: null` means `op` isn't a chat op. |
| `events[]` | transport message: `evt chat` |
| `invalid.params[]`, `invalid.results[]` | `{ op, json }` that must fail to parse |
| `invalid.events[]` | JSON strings that must fail to parse |
| `new.params[]`, `new.results[]` | `{ json, expected }` for `chat.new` (§8.2): its params `{ taskId }` and result `{ tabId }`. Extra fields are dropped. |
| `new.invalid.params[]`, `new.invalid.results[]` | JSON strings that must fail to parse |
| `taskNew.params[]`, `taskNew.results[]` | `{ json, expected }` for `task.new` (§8.4): its params `{ projectId, prompt, mode?, workspace? }` and result `{ taskId, tabId }`. Extra fields are dropped, `mode: null` is absent, and `workspace` is kept only when it is `true` (§8.6). |
| `taskNew.invalid.params[]`, `taskNew.invalid.results[]` | JSON strings that must fail to parse (a blank prompt and an unknown `mode` among them) |
| `taskClose.params[]`, `taskClose.results[]` | `{ json, expected }` for `task.close` (§8.7). Flags are kept only when `true`. An unknown `blocker` becomes `check-failed`. |
| `taskClose.invalid.params[]`, `taskClose.invalid.results[]` | JSON strings that must fail to parse (a result without `closed`, or `closed: false` without `blocker`, among them) |
| `tabClose.params[]`, `tabClose.invalid.params[]` | `{ json, expected }` for `tab.close` (§8.8) params `{ tabId }`, and JSON strings that must fail to parse |
| `pinSet.params[]`, `pinSet.invalid.params[]` | `{ json, expected }` for `pin.set` (§8.10) params `{ projectId, taskId?, pinned }` (`taskId: null` is absent), and JSON strings that must fail to parse |
| `image.params[]`, `image.results[]`, `image.invalid.params[]`, `image.invalid.results[]` | `{ json, expected }` for `chat.image` (§8.9) params `{ tabId, itemId, index, maxSide? }` (`maxSide` clamped to 64…4096) and results `{ mediaType, data }`, and JSON strings that must fail to parse |
| `settings.params[]` | `{ json, expected }` for `chat.settings` (§8.5) params `{ tabId, mode?, model?, effort? }`. `""` is kept (it means the default); `null` is absent. |
| `settings.invalid.params[]` | JSON strings that must fail to parse (no field to change and an unknown `mode` among them) |

Tolerance rules the samples exercise (a newer desktop must not break an older phone):
- An item or prompt with an unknown `kind` parses to `{ kind: "unknown", id, unknownKind: <the kind> }` and keeps its place. Its other fields are dropped.
- An unknown tool `status` reads as `"pending"`, an unknown notice `tone` as `"muted"`, and an unknown `process` as `"idle"`.
- Flags (`queued`, `failed`, `streaming`, `agent`, `always`) are either `true` or absent; `false` is dropped. `images: 0` is dropped.
- A known kind with a missing or wrong-typed required field fails the whole message.
- Parsed objects put the session fields in the order `busy, turnStartedAt, process, processError, permissionMode, model`, after `tabId`/`title` (view) or `t, e, tabId, seq` (event). Plain JSON equality doesn't care, but a byte comparison would.

## `push.json` (§7)

Hex fields are lowercase hex. Strings that go on the wire (`cap`, `data`, `sig`) are as sent.

| field | meaning |
|---|---|
| `register` | `{ phone: {seed, pub, deviceId}, token, env, ts, message, body }`. `message` is the exact string that is signed (JSON-encoded here so the newlines show), `body` the `POST /v1/push/register` JSON the phone sends. RFC 8032 Ed25519 is deterministic, so a deterministic signer (Node) must reproduce `body.sig` byte for byte. CryptoKit randomizes its Ed25519 signatures, so Swift instead checks that `body.sig` verifies against `phone.pub`, and that its own signature does too. |
| `cap` | `{ sealKey, nonce, payload, cap }`: sealing `payload` (as `{"d","g","t","e"}` JSON in that key order) with `sealKey` and the fixed `nonce` gives exactly `cap`; opening `cap` gives `payload`. |
| `payload` | `{ key, keyId, nonce, cases[] }`. Each case is `{ name, input, data, opened }`: the desktop seals `input` with `key`, `keyId` and the fixed `nonce` to exactly `data`; the phone opens `data` to `opened`. `opened` shows the cuts: title and body end in "…" at 120 and 400 characters, and the last case's body was shortened further so `data` fits in 3072 characters. |
| `params[]` | `{ op, params, parsed }`: the desktop's `push.*` params parser. Unknown `kinds` are dropped. |
